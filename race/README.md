# RACE — same agent, two surfaces

RACE is the hero demo for the YC Make Something Agents Want submission. One agent model does the same six tasks on six live websites twice, at the same time: once with a headless browser (standard Playwright MCP over CDP, `browser_evaluate` allowed, screencast shown live) and once with `clify` JSON CLIs (shell only). Both racers get the same prompt; only the tool surface changes. Every answer is checked against live data from the sites.

Run it on a Linux machine with Chrome (headless, `nice -n 10`, two racers at once, about 4 GB RAM for the browser racer), from the repo root, after `npm ci` in `clify/`. `race/bin/clify` runs this checkout's `clify/` (`RACE_CLIFY_DIR` overrides it); account commands are `clify` subcommands (`clify login|session|whoami <site>`). The agent's vault is `~/.clify-agent`.

## Round 3: signed-in SaaS dashboards (`tasks/accounts.json`)

Round 2 used public toy sites the model has memorised, and the browser racer just wrote its own scraper in page JavaScript. Round 3 is real logged-in work on dashboards of the clify agent identity's own accounts, plus one public forum:

| id | site | work | checked live by |
| --- | --- | --- | --- |
| updown | updown.io | add an HTTPS check for `example.com/race-<id>`, every 5 min, alias `race-<id>`; report its token | updown API (key read from the account's settings page) |
| healthchecks | healthchecks.io | add check `race-<id>`, tag race, period 1 h, grace 10 min; report its ping URL | project dashboard |
| svix | dashboard.svix.com | create app `race-<id>`, add endpoint `https://example.com/hooks/race-<id>`, list endpoints; report both ids | Svix API |
| appwrite | cloud.appwrite.io | in "My first project" › database `race`, create table `race-<id>` with a required string column `email` (255); report the table id | Appwrite console API |
| hookdeck | dashboard.hookdeck.com | connection `race-<id>`: new source → new HTTP destination `https://example.com/race-<id>`; report the source URL | Hookdeck API |
| forum | forum.rclone.org (public) | 3 newest non-pinned topics in "Suspected Bug" with who started each | Discourse JSON (snapshot at start and at check) |

**Same accounts for both racers.** Sessions come from the encrypted clify vault (`~/.clify-agent/vault.enc`). The clify racer gets a per-run clify home with the specs in `specs-generated/` (made by `clify add`, see below; only these sites, `CLIFY_NO_BUILTINS=1`) and a fresh vault that holds only those sites' saved sessions, no passwords; it is deleted when the racer ends. The browser racer's Chrome is loaded with the same saved browser storage state (cookies + localStorage) before the race starts, so both racers start signed in and the race measures the work, not the login.

**Three modes, labelled exactly:**

- **A · browser agent, clicks + screenshots** — Playwright MCP with `browser_evaluate` and `browser_run_code*` removed (`RACE_BROWSER_MODE=ui`). This is how consumer browser agents work. A run where mode A calls a page-JavaScript tool is marked invalid.
- **B · browser agent + page JavaScript** — the full Playwright MCP (`RACE_BROWSER_MODE=js`), the strong baseline.
- **C · clify, Bash only.**

A run is two racers at once on the same model: A vs C or B vs C. The video dashboard is two panels (A vs C); B's means are printed in the scoreboard footnote (from `results/accounts-modes.json`: A and C from round 5, B pooled over the B runs of rounds 4 and 5, since the browser racer does not use the specs) and in the results below.

**Clean-up.** Every object is named `race-<racer id>` (racer ids are `ui-HHMM`, `js-HHMM`, `clify-HHMM`). The runner deletes this run's objects before and after the race and on Ctrl-C. `node race/accounts/cleanup.mjs` deletes every `race-*` object on the five dashboards and checks that all saved sessions still work (the runner also refuses to start if one doesn't). Nothing else in the accounts is touched, and nothing is posted on the forum.

```bash
RACE_TASKS=race/tasks/accounts.json RACE_BROWSER_MODE=ui nice -n 10 node race/run.mjs     # A vs C
RACE_TASKS=race/tasks/accounts.json RACE_BROWSER_MODE=js nice -n 10 node race/run.mjs     # B vs C
node race/stats.mjs --modes race/results/accounts-modes.json race/runs/<run> ...
```

### Specs: generated by `clify add` (5 of 6), svix hand-written

The clify racer's specs in `specs-generated/` are made by `clify add` itself with the agent's saved sessions (`--account agent`, vault copy in a scratch `CLIFY_HOME`, deleted afterwards). Nobody edits them. `RACE_SPECS=race/specs-accounts` runs round 3's hand-written set.

| --- | --- | --- | --- |

On a public site whose API the model already knows (the forum, and the [bench](../bench/README.md#versus-an-agent-with-curl)), curl is as good or better.

## Run a live race

```bash
race/bin/live-race            # A vs C: deletes leftover race-* objects, checks every saved session, serves the dashboard on 127.0.0.1:8870, Enter starts the race
race/bin/live-race js         # B vs C
race/bin/live-race replay     # no live agents: the representative round-5 run, 4× after 10 s
race/bin/demo [replay|js]     # the same from another machine: RACE_BOX=<ssh host> (repo in ~/clify, or RACE_DIR) forwards the dashboard to 127.0.0.1:8790
```

Nothing opens by itself; view the printed URL in your own browser. When a race ends its objects are deleted and the browser racer's Chrome profile (which holds the session cookies) is removed, so repeat runs are safe. Without network, play `race/artifacts/accounts-4x.mp4` or `accounts-realtime.mp4`. If a saved session has expired, the preflight names it: `clify login <site>` with the agent's vault, or use the replay.

`checks.mjs` fetches the truth from the sites before the racers start (all pages, the Algolia API, the AJAX JSON) and verifies each racer's own FINAL ANSWERS block. The pizza check needs httpbin's echo in the racer's tool output. The room check reads the live room list after the racer finishes; the runner also polls it during the race and deletes the race rooms at the end.

The clify racer gets the hand-written specs in `specs/` (installed into a per-run `CLIFY_HOME`). `rbp` login returns a token that admin commands take as `--cookie token=...`.

## Run

```bash
nice -n 10 node race/run.mjs                      # Claude Code, claude-opus-5-5
RACE_AGENT=codex nice -n 10 node race/run.mjs     # Codex CLI, gpt-6.1-sol
node race/stats.mjs race/runs/<A> race/runs/<B> race/runs/<C>
```

`RACE_AGENT` picks the agent for both racers, so a run never mixes models. Claude runs use Claude Code's own login on the machine (`ANTHROPIC_API_KEY` is removed from the env). If an answer comes from any other model the run is marked INVALID. Codex runs use a private `CODEX_HOME` with only the model provider config. Built-in browsers, web search and sub-agents are off for both racers, and the browser racer has no shell.

Each run directory has `events.jsonl` (everything the dashboard shows), `summary.json`, a stream, prompt and stderr per racer, and the browser screencast frames.

## Metrics

- **Fresh tokens** = input + output + cache writes. **All tokens** adds cache reads.
- **Cost** is at list price and includes cache reads. Claude prices: $4 in, $20 out, $0.20 cache read, $8 for 1-hour cache writes. The final Claude number is Claude Code's own `total_cost_usd`. Codex cost is computed ($2 / $10 / $0.10).
- Usage updates on every model call. For Claude it comes from the stream's `message_start`/`message_delta` events (`--include-partial-messages`). For Codex it comes from `token_count` events in the session rollout file.
- **Turns · tools** = model calls · tool calls.
- **CPU** is % of one core. **RAM** is the RSS of the agent's process tree, sampled every 0.5 s. The browser racer's tree includes its Chrome, which also runs the dashboard screencast.
- **Per-site time** runs from the racer's `RACE_TASK_START` mark (or its first tool call on that site) to its `RACE_RESULT` mark (or its last tool call there).

## Grid: 6 browser agents vs 6 clify agents

`race/bin/grid` (or `race/bin/demo grid` from your own machine) runs the six signed-in tasks as six separate races at once: on each site a browser agent (mode A) and a clify agent (mode C) start together, so twelve Claude Code agents run in parallel. The page (`race/web/grid.html`, served by `race/grid-server.mjs`) shows one tile per agent: the browser's live screen on the left, the clify agent's terminal on the right, each tile's time and a ✓ when the run's check confirms the object on the live site. Each site's run is a normal run directory (`race/runs/grid-<stamp>/<site>/`), cleaned up like any race. `race/bin/grid replay` plays the recorded grid run named in `results/grid-replay.txt`.

## Dashboard, replay, recording

```bash
node race/server.mjs                                    # live: newest run
node race/server.mjs --replay race/runs/<run>            # replay at real speed
RACE_REPLAY_SPEED=4 RACE_REPLAY_FAST_AFTER_MS=10000 node race/server.mjs --replay race/runs/<run>
nice -n 10 node race/record.mjs race/artifacts/race.mp4    # records whatever the server plays
```

The server binds to `127.0.0.1:8870` (`PORT` overrides it). In replay the clock starts 1.5 s before the racers. With `RACE_REPLAY_FAST_AFTER_MS` the first N ms play at real speed and the rest at `RACE_REPLAY_SPEED`, with a "4× SPEED" badge in the header. `record.mjs` pipes headless-Chrome screencast frames into ffmpeg at a fixed 30 fps (1920×1080, H.264). It stops 9 s after the replay ends and saves `<out>-final.png`; set `RACE_SHOTS=30000,60000` for more screenshots.
